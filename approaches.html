Interaction technique — notes

Particle name reveal, two ways

A dust field that assembles into a name as the cursor sweeps across it. Both versions below share the same base technique — sample text into points, animate anonymous dust motes toward them — but differ in how a mote gets assigned to a letter. Try both; the difference is in how "productive" a sweep feels.

The shared foundation

Neither version hand-plots pixel coordinates. The name is drawn onto an offscreen canvas with fillText(), then read back with getImageData() — any pixel with alpha above a threshold becomes a target point. That point cloud is the shape of the name. Each point gets one particle; particles start scattered randomly and ease toward their assigned point (x += (targetX - x) * 0.1) once captured.

Approach A

Pre-assigned particles, gated by letter

Every particle is tagged with its destination letter up front, at build time. Only particles belonging to the current letter can be captured — sweep near an "H" particle while "S" is still active, and nothing happens. This guarantees strict letter-by-letter order, but most of the dust you pass over at any moment belongs to a future letter and simply can't react.

Only the active letter's particles respond — try hovering where a later letter will be. 
function captureNear(x, y) {
  if (activeCharIndex >= NAME.length) return;
  var bucket = byChar[activeCharIndex];   // only THIS letter's particles
  for (var i = 0; i < bucket.length; i++) {
    var p = bucket[i];
    if (p.captured) continue;
    var dx = p.x - x, dy = p.y - y;
    if (dx*dx + dy*dy <= CAPTURE_R * CAPTURE_R) {
      p.captured = true;
      charRemaining[activeCharIndex]--;
    }
  }
  if (charRemaining[activeCharIndex] <= 0) activeCharIndex++;
}

Approach B

Anonymous particles, priority queue

Particles carry no destination at all until the instant they're captured. Every letter-slot the name needs is pre-sorted once into a priority queue — mostly by letter, with a little random jitter so adjacent letters blend at the boundary instead of hard-cutting. Any nearby dust mote can be captured; it just pops whatever's next off the queue. Sweep anywhere and you're almost always doing something useful.

drag to sweep 0%
Every nearby particle is catchable — sweeping is never wasted. 
function captureNear(x, y) {
  if (nextSlotIndex >= slots.length) return;
  for (var i = 0; i < particles.length; i++) {
    var p = particles[i];
    if (p.isAmbient || p.captured) continue;
    var dx = p.x - x, dy = p.y - y;
    if (dx*dx + dy*dy <= CAPTURE_R * CAPTURE_R) {
      var slot = slots[nextSlotIndex++];   // pop the queue
      p.tx = slot.x; p.ty = slot.y;        // assigned only now
      p.captured = true;
    }
  }
}

// priority = mostly letter order, blurred at the edges
priority = charIndex + (tier / TIER_COUNT) + (Math.random() - 0.5) * JITTER;

Comparison

Which one to use

TraitA — gatedB — priority queue
Sweep efficiency~1/n of dust usable at a time (n = letters)nearly all dust usable until queue empties
Visual feedbackswept areas often look unchangedswept areas visibly empty out
Letter orderhard-guaranteed sequentialmostly sequential, soft overlap at edges
Particle statetx/ty fixed at build timetx/ty assigned at capture time
Code complexityper-letter bucketing + remaining-countsone sorted array + a cursor
Why B ended up better here: the failure mode of A wasn't the ordering logic, it was that most dust is inert most of the time, which reads as unresponsive. Decoupling "what you touched" from "what it becomes" (only resolved via a queue pop) fixes that without giving up the letter-by-letter feel — the queue's sort order still does that work.

Custom fonts

Do you need to supply pixel coordinates?

No — that's the point of sampling from a canvas instead of hand-plotting a point list. ctx.font accepts any font family the browser can render, including a custom one. Swap the family name and the exact same fillText + getImageData pipeline picks up the new letterforms automatically.

The one real gotcha: if the custom font hasn't finished loading yet when you draw and sample, the canvas silently falls back to the platform default font — no error, it just quietly samples the wrong shape. Load the font and wait for it before sampling: 

@font-face {
  font-family: "MyDisplayFont";
  src: url("./MyDisplayFont.woff2") format("woff2");
  font-weight: 700;
}

<script>
  // Match this string EXACTLY to what you'll use in ctx.font later
  document.fonts.load('700 200px "MyDisplayFont"').then(function () {
    buildParticles(); // now safe to sample — the font is actually loaded
  });

  // Alternative: wait for every declared @font-face to be ready
  // document.fonts.ready.then(buildParticles);
</script>

Then just point ctx.font at it, same as the built-in demos above: 

octx.font = '700 ' + fontSize + 'px "MyDisplayFont"';
octx.fillText(NAME, startX, h / 2);
var pixels = octx.getImageData(0, 0, w, h).data; // unchanged from here on
A variable-width font (script/cursive faces especially) will change your per-character bounds calculation — the demos above measure each character's width individually via measureText() to figure out which letter a given pixel belongs to. That still works with any font; you just may want to sanity-check the bounds visually once, since script fonts can have overlapping letter advances.
Sampling technique: canvas.fillText() → getImageData() → alpha-threshold point cloud → one particle per point.
